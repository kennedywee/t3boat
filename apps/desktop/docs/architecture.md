# How t3boat works

Internals. For what t3boat is and how to install it, see the [README](../../../README.md).

```
T3 Code ──ws──> localhost proxy (t3boat) ──https/wss──> T3 server on a Boat sandbox
                    │                                     └─ watchdog: stops the sandbox when idle
                    └─ boat CLI: new / resume / host / exec / delete
```

- **Machine**: a Boat sandbox running the T3 server pinned to your desktop app's version, as a systemd user service bound to loopback. Boat relays a public HTTPS URL to it; T3's own pairing auth protects it.
- **Proxy** (`src-tauri/src/proxy`): one `http://localhost:<port>` per machine; that is the address T3 Code pairs with, so a new sandbox IP after resume never matters. The proxy is its own auth server towards T3 Code and uses its own long-lived token upstream. T3 Code sends its token as `Bearer` or, paired since it supports renewal, as `DPoP` with a proof; the proxy takes the token under either and does not check the proof, since it answers loopback only.
  - Awake: frames pass through (minus `directEndpoints`, which would let T3 Code bypass the proxy). Snapshot-style subscriptions and some reads are recorded, and the images T3 Code loads are kept on this computer (`proxy/assets.rs`).
  - Asleep: answers pings, probes, config and other recorded subscriptions, and serves the shell and the chats from the state captured as the machine went to sleep, so opening a chat does not wake it. Images shown before stay visible.
  - Anything else wakes the machine: `boat resume`, then the held request goes upstream, then the socket closes so T3 Code reconnects to the live server and resyncs. A message sent to a chat is accepted at once instead, since a wake outlasts T3 Code's 15 s slow-request warning: it shows as sent, wakes the machine and goes upstream before T3 Code reconnects; one the server refuses is reported as a notification. Only the side information T3 Code asks for on its own as it starts and as a chat opens (git status, branch, terminals, servers, the pull request's badge and checks, linked chats, the count of older chats, the branch list, the changed-files count) never does: it is shown as last seen, and with nothing recorded it stays unanswered until the machine wakes for something else. Worktree setup progress, a chat's preview tabs and their events are never shown from a recording (a stale one would hold Send, or close or reopen tabs). What T3 Code asks for on its own but a person also waits for is shown as last seen too, but wakes the machine when never seen: the linked machines (Send), a pull request's details (a quick merge, the checks popover), a related chat's title, the automations and the archived chats (their settings pages), the chats under "Show more", the files of a commit or of uncommitted changes, an MCP app's tool definition and resources (a click in the app, an approved download), the voice status of the machine dictation goes to (a mic click). Images never do either: one never seen on this computer shows as unavailable until the machine is next up. A finished command's output is kept the first time its row is expanded and shown from then on; one never expanded wakes the machine.
- **Streams** (`proxy/media.rs`): device and browser-preview streams pass through while the machine runs, close codes included. T3 Code opens them with a ticket the proxy issues itself and keeps retrying while one is on screen, so a stream never wakes a sleeping machine (it answers 503) and only input in it (a click, a key) counts as using the machine: watching does not keep it up. Any other WebSocket (dictation's `/ws/voice`, and whatever T3 adds) is relayed the same way but wakes the machine: a person opened it.
- **Linked** (`machine/link.rs`, `proxy/link.rs`): with linked environments on in T3 Code (Settings → Labs), every machine is linked into the desktop app's own T3 server through the proxy, with full access as the ceiling, so agents on this computer can work on it (`delegate_task`, the thread tools) with nothing to set up. Links last 30 days; each wake renews one in its last week. The link's status probe is answered from the last descriptor and never wakes the machine; a tool call does, and counts as using it. The handshake that opens a link's MCP session is given 3 s by T3, less than a wake can take, so for a sleeping machine the proxy answers it itself: the call that follows waits for the wake, the machine refuses the unknown session and T3 opens a real one.
- **T3 Connect** (`machine/connect.rs`): T3's own route for other devices (its phone app, a browser), a tunnel the machine dials out to Cloudflare under a stable hostname. "Turn on" runs T3's `t3 up --connect --headless --yes` on the machine, opens its sign-in page here and waits until the machine is reachable, then turns on "Hold webhooks while offline": T3 Connect's relay keeps a webhook sent to a sleeping machine (up to 24 h) and delivers it as the machine wakes. The tunnel comes back by itself on every wake. Nothing wakes a sleeping machine for a phone: only t3boat on this computer wakes it. Provisioning names the machine in `/etc/machine-info`, so other devices show its t3boat name, not the sandbox's hostname.
- **Ports** (`machine/ports.rs`): a machine's dev servers in this computer's own browser. Each forwarded port is a listener of t3boat's on this computer's loopback at the same number, so code that names `localhost:4000` works unchanged, and a monorepo's apps reach each other from the browser as they do locally. Behind each listener runs one `boat forward` (it takes one port) on a spare local port; the listener relays to it. Owning the listener is what tells a port taken on this computer from a tunnel that failed, and what makes a new connection count as using the machine: the watchdog hears of it, so the machine stays up while someone clicks around and sleeps 5 minutes after the last request. What the browser sends on a connection already open (a further request, a WebSocket message) counts the same; a keepalive's few bytes do not, so a page left open on hot reload does not keep it up. The ports turned on are kept in the machine's record: the tunnels end when it sleeps and come back when it wakes, and one that dies is started again by the loop. Nothing wakes a machine through a forward: a sleeping machine's ports refuse connections. Turning one on does wake it. The list of what listens comes from `ss` and `docker ps` on the machine (a container's published port carries the container's name), asked only when the details view opens or on "Rescan": T3's own discovery misses containers. Ports below 1024, T3's and the watchdog's, and the image's own services are left out. A port can also get a **link**: Boat's own HTTPS address for it (`boat host`, `https://<sandbox>-<port>.on.boat.dev?_token=…`), which opens on any device with nothing running here and stays the same across sleeps. Links are private: the token in the address is the access, kept with the machine's record. How the port listens decides how Boat reaches it, so a link is made after a fresh scan: a loopback-only service gets Boat's relay (`--localhost`), one on every address must not, since the relay would hold its port. Links are also made on the machine itself, by a project's own script or an agent (Boat's `host` command there), so every scan reads the machine's link list and the record follows it: a link made there shows here with its token, ready to open. Removing a link runs `host hide` on the machine, which keeps the token, so a later link is the same address. An app behind a link runs under another host name: one that checks its host (Vite's `allowedHosts`, Rails' `config.hosts`) or redirects to `localhost` refuses until its own config allows it, which is why forwarding is the way that needs nothing. Traffic through a link is not seen here, so it does not keep the machine awake. On Linux the tunnels die with the app however it ends; elsewhere a quit ends them and a crash can leave them behind, holding only their spare port.
- **Watchdog** (`src-tauri/src/machine/watchdog.mjs`, on the sandbox): the machine decides when to sleep, so it finishes its work and then sleeps even with the laptop closed. Idle = no agent run in flight (incl. waiting on an approval), no sustained CPU use (a build), no "stay awake", no work due within 5 minutes, and nobody using it for 5 minutes: through t3boat, or in T3 from any other client (a phone through T3 Connect), seen as orchestration events only a person causes (opening a chat, pinning, archiving, ...). If T3 stops answering it counts as busy for at most 30 minutes; until it first answers after a boot it is starting, not failing. Before stopping it drains: publishes a manifest of orchestration high-water marks, the proxy captures that state and acks, the watchdog stops at that sequence (`boat stop self`) and says so. Before draining it saves the disk as a Boat snapshot (`boat snapshot self`, ~30 s); any use meanwhile calls the sleep off.
- **Scheduled work**: T3 runs automations, held webhook runs and an agent's resume after a usage limit on in-process timers, so on a sleeping machine they would not run, and T3 skips a daily automation it missed by over 10 minutes. The watchdog reports the next due time from T3's database; t3boat keeps it and wakes the machine 2 minutes ahead, for work that came due after the machine went to sleep (what came due while it ran had its chance). The watchdog then waits for it instead of sleeping. Only while t3boat runs: Boat cannot resume a sandbox on a timer.
- **Capture**: one shell snapshot, unfiltered, which serves every client whatever it asked to leave out; and the chats, one file each on this computer, named by thread id, thread sequence and snapshot encoding (`proxy/threads.rs`). A sleep fetches the files it is missing, most recent chat first, and deletes every other one: the files are the store, there is no index. It has 12 s for all of it, since the watchdog stops 20 s into a drain; a chat that did not make it wakes the machine when opened.
- **Capture freshness**: the proxy trusts its capture only when the watchdog confirmed stopping at the captured sequence and Boat's `stoppedAt` follows it. Otherwise (laptop closed while the machine ran) the first request that needs state wakes the machine once to resync. Recorded reads carry an epoch that moves on whenever an agent works or the user acts, so no outdated file or diff is served; recorded subscriptions (git status, terminals, ...) and the branch list a chat displays replay as last seen instead. The project's `t3.json`, which T3 Code reads on every chat open, follows the epoch too, so each sleep reads the recorded ones again: T3's editor saves over the file whatever it was shown, and a new thread's environment is decided from it. The automations T3 Code was shown are read again at each sleep as well: its editor saves every field of a task as it was shown. A branch search, a further page of branches and the one branch read T3 Code decides on (is this branch checked out in that worktree?) follow the epoch like any other read.
- **Expiry**: chats leave the store 3 days after they are settled, recordings 3 days after T3 Code last asked for them, images with the recording that points to them.
- **Resize**: Boat resumes a sandbox onto any size; an idle machine is moved right away and keeps its "keep awake", a working one (an agent or a build) moves when it next sleeps.
- **Upgrades**: on wake, a machine whose T3 version or provisioning scripts differ from the app's is re-provisioned (`provision.sh` is idempotent). A new T3 version also drops the recorded streams and stored chats: they are in the old server's encoding.
- **Keep-alive**: Boat keeps a stopped disk 14 days; machines asleep 12 days get a short wake.
- **Restore**: with t3boat not running for those 14 days the disk is gone. The snapshot saved at every sleep (`t3boat-<name>-<id>`, one of the plan's saved snapshots per machine) has no expiry: the next wake creates a new sandbox from it. The machine keeps its id, port and T3 environment; only its sandbox and addresses change.
- **Two computers** (`App::adopt_machine`, `machine/adopt.sh`): a machine can be on every computer signed in to the same Boat account. It keeps a record of itself in `~/.t3boat/config.json` (its id and name, the watchdog's secret, its T3 version). t3boat lists the account's `t3boat_<name>` sandboxes that are not on this computer; "Add here" wakes one, reads the record, issues this computer its own T3 token and adds the machine to T3 Code. Nothing else changes there, and nothing is copied from the other computer. Each computer then runs its own proxy and loop for the machine, with its own captures.
  - Sleep: every app names itself to the watchdog (`x-t3boat-client`). The first ack of a drain is held up to 10 s while another app seen in the last 15 s has not acked, so each captures the same state and sees the stop. An app that missed it has no confirmed capture and wakes the machine once to resync, as after "laptop closed while the machine ran".
  - T3 version: the watchdog's status carries the installed version. An app that sees one it did not install notes it and drops its recorded streams and stored chats. A newer version that another computer installed is never downgraded: the user is told to update T3 Code on this computer.
  - Size: Boat holds it. Each app follows the size Boat reports, except between a resize it asked for and the resume that applies it, so a wake from one computer keeps a resize made on another.
  - The record is not trusted: the id it gives names a local folder, so only `[A-Za-z0-9_-]` is accepted.
  - Not handled yet: a delete on one computer deletes the machine for all, and the others show "Deleted on Boat". A restore gives the machine a new sandbox, which the other computers do not follow: there it shows as deleted. "Add here" on the restored one puts it back in that row, with the same local port and T3 Code pairing. Two apps that restore at the same moment would each create a sandbox. The fleet setting and the GitHub login (its token and what it is for) are per computer: the last one to provision wins.
- **Projects** (`projects.rs`, `machine/projects.rs`): t3boat moves no code itself; it drives T3 Code's own flow through T3's API. "Add a project" (in a machine's details, or picked when creating one) does what T3's "Add to another machine" dialog does: reads the project and its `.env` files from the desktop app's server (t3boat holds its own read-only session there, "t3boat" under Settings → Connections), then `projectClone.start` on the machine, which clones over HTTPS and registers the project with progress in T3 Code, then `projects.writeFile` for the env files. Private repos need nothing extra: Boat signs every sandbox in to GitHub as the Boat account (`gh` with git's credential helper, renewed on each resume), which T3's clones and pushes use. The machine's projects are read from its shell when it runs or sleeps, so listing them never wakes it. Work goes back the way T3 Code does it: push or open a PR. Agents use `add_project` here, or T3's own tools through the link (`t3_project_clone`, `delegate_task`, `t3_thread_launch` with the machine's `environmentId`).
- **GitHub uploads** (`github.rs`, `machine/provision.sh`): Boat's login on a machine is its GitHub App's token (`ghu_…`), and GitHub's upload server refuses those, so `gh pr edit --attach shot.png` fails there ([cli/cli#14309](https://github.com/cli/cli/issues/14309)). "GitHub login" in the settings adds the user's own login for that one thing, or with "Use for everything" for all of `gh` and git (below). The sign-in runs this computer's `gh auth login --web` with its own `GH_CONFIG_DIR` and `--insecure-storage`, so the user's `gh` login and keyring are neither read nor changed; the token is kept in the state file. Provisioning brings it to `~/.t3boat/gh-upload-token` (mode 600) inside the uploaded script, never on a command line (`boat history` keeps those), upgrades `gh` from GitHub's apt repo (the image's own predates `--attach`), and writes `~/.local/bin/gh`, which is ahead of Boat's on PATH: `gh pr|issue create|edit|comment` with `--attach` as a flag runs `/usr/bin/gh` with `GH_TOKEN` set from the file, anything else runs it unchanged (an `--attach` that is another flag's value, as in `--body '--attach'`, is text). That part of provisioning is its own script (`machine/gh-uploads.sh`) and restarts nothing. Each machine records what it was last given (`gh_uploads_revision`: the script and the token, or none), apart from the provisioning revision, and its loop runs the script whenever that differs from the settings: within seconds on a machine that is up, agents working or not, as it wakes on a sleeping one, and again a minute after a failed try. Changes to a machine run one at a time, and the record is cleared before each, so a disconnect is never skipped. The script has two parts: `apply` (the token off first, then the wrapper and the token) runs first, inside that queue; when it fails, `upgrade` (apt, no token) runs outside the queue and `apply` once more, so neither a disconnect nor a new login waits for a package install. `apply` fails when a token is connected and `gh` still has no `--attach`, which gets it tried again. The token acts as the user and is in the machine's snapshots; disconnecting removes it from machines, and only GitHub revokes it.
- **GitHub login for everything** (`machine/gh-uploads.sh`): Boat's login reaches only the repos its GitHub App is installed on, with the app's permissions. With "Use for everything" on, machines use the user's own login for all of `gh` and git instead. `apply` writes `~/.t3boat/gh-everything`, and the wrapper then sets `GH_TOKEN` for every command, which `gh` reads ahead of Boat's `GITHUB_TOKEN` and its `hosts.yml`. Git follows without a change of its own: Boat's `~/.gitconfig` asks `!gh auth git-credential` for the password, and `~/.local/bin` is first on PATH (in shells and in the T3 service), so git runs the wrapper and gets the same token. Nothing of Boat's is edited, so its sign-in on each resume undoes nothing, and with the file gone the machine is back on Boat's login. `gh auth login`, `logout`, `refresh`, `setup-git` and `switch` run unchanged: `gh` refuses them with a token in `GH_TOKEN`. `apply` asks `git credential fill` for github.com afterwards and fails when the answer is not the token, which gets it tried again. The sign-in asks for the `workflow` scope too, which a push that changes a workflow file needs; a login from before that keeps its scopes until reconnected. A wake applies a change made while the machine slept before it lets work through (it waits up to 20 s for that), so the first clone or push already uses the right login. Git's author is not changed: a machine keeps the author it was created with. Not covered: a tool that reads `GITHUB_TOKEN` itself or runs `/usr/bin/gh` by its full path still acts as Boat's login. The mode is part of `gh_uploads_revision`, so a change reaches machines the way a new token does.
